# ModuleBitrixNotify — диагностика и типовые проблемы

## Где смотреть логи

```bash
# На АТС (SSH)
tail -f /var/log/messages | grep -i bitrixnotify
# или в bash-микрокернеле MikoPBX
grep -i "ModuleBitrixNotify" /var/log/messages | tail -50
```

Модуль пишет: «Not initialized: …» (нет настроек/токена), ошибки curl, отказы публичного endpoint.

## Уведомления вообще не приходят

1. **Проверьте настройки через REST** (с админ-машины, под админ-кей/сессией):
   `GET /pbxcore/api/modules/ModuleBitrixNotify/check` — поля `tokenSource`, `initialized`, `defaultRecipients`.
2. Кнопка **«Проверить подключение»** на странице модуля — то же самое без консоли.
3. Если `initialized:false` — прокомментируйте, какого источника не хватает: поле формы → токен из URL вебхука → env `BX_WEBHOOK_TOKEN` → файл `/etc/bitrix-webhook-token`.
4. Кнопка **«Тестовое сообщение»** — она реально дергает `im.notify`: увидите `delivery[uid]`.

## Пропущенные не приходят, но тестовое сообщение доходит

- **Ядро < 2026.4**: в poll-режиме сообщение приходит с задержкой до минуты — подождите и проверьте;
  «Проверка» покажет `workerMode: polling`.
- Уведомляются **только входящие внешние пропущенные**: `did != ''` и звонящий не из списка внутренних номеров.
  Пропущенные внутренние на внутренние намеренно не отправляются.
- `is_app` непустое (звонок через очередь/IVR-приложение) — пропускается.
- Антифлуд: если несколько пропущенных подряд на одного получателя с `throttle_sec > 0`, часть уведомлений осознанно подавляется — оставьте `0`, чтобы точно проверить.

## Ловится не тот получатель

Правило выбора получателя: внутренний номер (`dst_num`) есть в карте «Персональные» → уведомление **только** ему; иначе — всем из списка «по умолчанию». Проверьте пары в форме (`201 = 1711`, разделители `;` или перенос строки).

## Токен / портал

- `curl error: 28 operation timed out` — портал не отвечает с АТС: проверьте доступность
  `https://company.bitrix24.ru/rest/…/im.notify.json` с самой АТС (firewall/DNS).
- `error: insufficient_scope` — вебхуку **не выдано право `im`**. У входящего вебхука права
  задаются при создании; отредактировать их у существующего может не получиться —
  пересоздайте вебхук и на шаге «Права доступа» отметьте **`im`** («Чат и уведомления»).
- `error: INVALID_CREDENTIALS` — не найден активный вебхук с таким `user_id` и секретным кодом:
  проверьте токен и что вебхук не удалён. После замены токена введите новое значение явно —
  пустое поле не затирает сохранённый токен.
- `error: ERROR_METHOD_NOT_FOUND` — метод не найден: проверьте, что URL имеет вид
  `/rest/<индекс>/<токен>/<метод>.json`. Без индекса приложения (`/rest/<токен>/…`) Битрикс24
  отвечает именно этой ошибкой; поле «Вебхук Bitrix24» с полным URL решает это автоматически.
- Битрикс24 принимает только `form-urlencoded` — модуль так и делает; если отправляете из последующих интеграций JSON вручную — «зависнет» без эффекта (проверенный кейс из опыта relay).

## Публичный endpoint отдаёт “Forbidden”

- Тумблер «Разрешить отправку без авторизации» выключен ИЛИ секрет пустой в настройках;
- секрет не совпал (проверяйте лишние пробелы/кавычки при передаче через shell);
- антифлуд вернул `Throttled` — это не Forbidden, отдельный код в `messages`.

## Модуль установился, пункта в меню нет

После установки модуль добавляет запись меню (addToSidebar при установке). Если пункта нет:
1. Переустановите модуль (uninstall → install);
2. очистите кеш вольта админ-панели (перевход/перезагрузка помогает из-за того, что меню собирается кешом).

## Обновление с 1.x

Схема таблицы `m_ModuleBitrixNotify` обновляется установщиком автоматически (`createUpdateDbTableByAnnotations`): новые колонки (`numbers_map`, `notify_ring`, `template_*`, `throttle_sec`, `public_api_enabled`, `api_secret`) добавятся при установке пакета 2.0.0. Старое поле `watch_numbers` остаётся в таблице, но модуль его не использует — фильтрация заменена правилом «только входящий внешний» и картой получателей. Настройки (портал/токен/получатели) сохраняются.
